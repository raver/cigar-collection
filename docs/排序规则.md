# 烟标排序规则

> 最后更新：2026-07-05
> 涉及改动：PR #（Sort Key 语言前缀 + API 排序）

---

## 排序策略

### 规则

烟标列表按名称排序，采用**中文在前、英文在后**的分组策略：

1. **中文组** — 名称首字符为汉字（CJK 统一表意文字）的烟标
2. **英文组** — 名称首字符为非 CJK 字符（拉丁字母、数字、符号等）的烟标
3. 各组内部按拼音/字母升序排列

### 排序效果

```
cn-bai-hua        | 百花           ← 中文组，拼音序
cn-hong-shuang-xi | 红双喜
cn-sheng-li-victory| 胜利-Victory  ← 混合名，首字"胜"归中文组
cn-yang-jin-hua   | 洋金花
cn-zhong-hua      | 中华
──────────────────────────────── 分组线
en-camel-blue     | Camel Blue    ← 英文组，字母序
en-hilton         | Hilton
en-marlboro-red   | Marlboro Red
en-victory        | victory
```

### 实现方式

- `name_sort_key` 列存储排序键，格式为 `{语言前缀}-{拼音/字母键}`
- 语言前缀：`cn-`（中文）、`en-`（英文）
- 拼音/字母键由 `buildCigarNameSortKey()` 函数生成（见 `api/src/services/cigar-sort.ts`）
- 数据库查询统一按 `name_sort_key ASC, id ASC` 排序

## 核心决策权衡

### 决策 1：语言分组 vs 混合排序

| 方案 | 做法 | 优缺点 |
|------|------|--------|
| **分组排序（采用）** | 中文一组在前，英文一组在后 | ✅ 访客先浏览中文老烟标，叙事感强；✅ 类似微信通讯录模式 |
| 统一混合排序 | 中文转拼音后，与英文统一按 A-Z 排列 | ⚠️ "a-shi-ma" 与 "camel-blue" 交错排列，缺乏分组语义 |

**行业参考**：
- 类似微信通讯录（中文拼音在前，英文在后）
- 多语种书目系统中也有按文字体系（script-grouped）分组的先例
- 与电商（淘宝/京东）的统一混合排序不同，烟标收藏更侧重叙事体验

### 决策 2：前缀方案

| 方案 | 前缀 | 排序表现 | 优缺点 |
|------|------|----------|--------|
| **`cn-` / `en-`（采用）** | 语义前缀 | `"c"` < `"e"` → 中文组在前 | ✅ 可读性强，一眼识别；✅ 自然排序 |
| 数字前缀 | `1-` / `2-` | `"1"` < `"2"` → 中文组在前 | ⚠️ 可读性差，未来数字可能冲突 |
| 大写前缀 | `CN-` / `EN-` | 大写 < 小写（ASCII），排序不稳定 | ❌ 与已有小写 key 排序混乱 |

### 决策 3：语言判断依据

| 方案 | 判断方式 | 示例 |
|------|----------|------|
| **首字符（采用）** | 名称第一个字符是否 CJK | `胜利-Victory` → 中文组（`cn-`） |
| 整体判断 | 名称中是否有任意 CJK 字符 | 同上（结果一致） |
| 字符占比 | 中文占比 > 50% → 中文组 | `AB胜利` → 英文组（若按占比则英文多） |

采用首字符判断的原因：实现清晰、无歧义，且混合名称（如 `胜利-Victory`）的首字符往往决定了其主要语言归属。

### 决策 4：排序键存放位置

| 方案 | 做法 | 优缺点 |
|------|------|--------|
| **数据库列 + 索引（采用）** | 预计算 `name_sort_key` 列，B-tree 索引 | ✅ 排序 O(log n)，前端零计算；✅ 分页/筛选查询可复用；⚠️ 名称变更需同步更新 key |
| 运行时转换 | API 查询时动态拼音转换 | ❌ 每次查询 O(n log n) 全量计算，性能差 |
| 前端排序 | 返回原数据，前端排序 | ❌ 分页困难，JS 端拼音转换库大 |

## 排序键生成逻辑

见 `api/src/services/cigar-sort.ts`：

1. 名称去首尾空格，空值返回 `cigar-unknown`
2. 判断首字符是否 CJK → 确定前缀 `cn-` 或 `en-`
3. 纯 CJK 名称 → 逐字符转拼音（`pinyin-pro` 库，无音调），连字符连接
4. 纯拉丁名称 → 小写 + 去除非字母数字字符（`normalizeString`）
5. 混合名称（如 `胜利-Victory`）→ 分段处理，CJK 段转拼音，拉丁段 normalize，`-` 连接
6. 最终返回 `{前缀}{拼音/字母键}` 或 `cigar-unknown`

## 迁移与兼容

- 数据迁移：`drizzle/0002_cigar_sort_prefix.sql` — 为现有 `name_sort_key` 加前缀
- 迁移幂等性：`WHERE name_sort_key NOT LIKE 'cn-%' AND NOT LIKE 'en-%'` 防止重复执行
- 管理后台"按名称重建排序键"按钮（`POST /admin/api/cigars/sort-by-name`）作为兜底工具，可随时重算所有排序键

## 未来考虑

- 纯数字或符号开头的烟标名归入英文组（`en-`），与现有 `normalizeString` 逻辑一致
- 如需调整分组方式（如改为混合排序），只需修改 `buildCigarNameSortKey` 的前缀策略，无需改 schema
- 当前 `name_sort_key` 类型为 `varchar(255)`，最长 key 约 50 字符，空间充足
